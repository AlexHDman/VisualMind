# MASTER ARCHITECTURE

Этот документ объединяет `AI VisualMind Architecture Summary` и `VisualMind Studio Summary`. Повторяющиеся положения сведены в единые формулировки; уникальные положения сохранены.

## Architecture

### Назначение и границы системы

AI VisualMind развивается как локальный workspace / AI Creative Studio для создания рекламных и визуальных материалов: постеров, изображений, видео, презентаций, анимации и связанных креативных результатов. Его основой являются структурированные знания, а не отдельные файлы или технические интеграции. Система организует контекст клиента, брендовые материалы, шаблоны, стили, промпты, референсы и результаты так, чтобы они были понятны человеку и в дальнейшем могли использоваться AI-инструментами.

На текущем этапе существуют логика и Markdown-контракты. Не реализованы код, AI-интеграции, базы данных и автоматизация. На этой границе не создаются Python-код, GUI, базы данных, JSON/YAML/XML, Graph Engine, Prompt Engine, AI-модели или AI-интеграции.

Архитектура независима от конкретных AI-моделей, поставщиков и внешних инструментов. Technology Map может меняться без изменения архитектурных контрактов.

### Workspace и knowledge layer

- Workspace включает клиентские проекты, общую библиотеку знаний, workflow-документы, конфигурации, рабочую область, экспорты, логи, документацию и служебные сценарии.
- Клиентские пространства существуют для Estates, FOHOW, Dental, Outdoor Ad-Makers и Sports Equipment. Для каждого используется структура: `brand`, `projects`, `templates`, `prompts`, `styles`, `characters`, `source_assets`, `generated_assets`, `exports`.
- Knowledge Base хранится в Markdown.
- Библиотеки знаний включают `brands`, `templates`, `styles`, `prompts`, `characters`, `reference_materials` и общие вспомогательные библиотеки материалов.
- Основная рабочая единица знаний — независимый Knowledge Base object с постоянным идентификатором, описанием, связями и жизненным статусом. Объекты атомарны и подчинены стандартам объектов, именования и отношений.
- Knowledge Pack — контекстный контейнер и основная единица организации знаний для клиента, бренда или задачи. Он не заменяет объекты и не закрепляет их за одним контекстом: один объект может использоваться в нескольких pack-ах.
- FOHOW — первый Reference Project для практической проверки решений перед их предложением другим клиентам. FOHOW Core Pack — первый pack; его развитие идёт отдельными утверждёнными этапами.

### Объектная модель и контракты

- Первый полный бренд-объект — `BRAND-FOHOW-001`; `BASIC_COURCE-001` сохраняется как legacy template object.
- Новый объект использует единый стандарт `OBJECT_STANDARD.md` и создаётся по `KNOWLEDGE_TEMPLATE.md`.
- Поля объекта: постоянный ID, читаемое имя, категория, версия, автор, даты, описание, purpose, теги, связи, связанные объекты, файлы, preview, notes и status.
- Новый ID имеет формат `CATEGORY-NAME-XXX`, создаётся один раз, уникален и не изменяется. Предконвенционные IDs сохраняются как legacy.
- Утверждённые категории: BRAND, STYLE, TEMPLATE, CHARACTER, PROMPT, PALETTE, LIGHTING, LAYOUT, TYPOGRAPHY, ICON, LOGO, PRODUCT, REFERENCE, WORKFLOW.
- Разрешённые семантические отношения: `uses`, `inherits`, `belongs_to`, `contains`, `depends_on`, `related_to`, `recommended_for`, `requires`, `based_on`, `references`, `compatible_with`, `derived_from`.
- Утверждённые типы Knowledge Pack: Core, Brand, Product, Marketing, Speaker, Training, Event, Visual, Media, Sales и Reference Pack.

### Engine-модель и архитектурные ограничения

Пользователь может работать голосом или текстом. Voice Interpreter концептуально преобразует голос в нормализованный текст; текстовый ввод нормализуется напрямую. Intent Interpreter определяет смысл запроса и выделяет object IDs, действия, значения и layout-изменения. Action Dictionary переводит обычные формулировки в стандартные действия, а Object Dictionary — человеческие названия элементов рекламного материала в устойчивые object IDs. Утверждены Action Dictionary из 50 распространённых действий и Object Dictionary из 50 объектов рекламного постера.

Creative Brief Engine помогает сформировать идею через вопросы и варианты выбора. Project Wizard ведёт по фиксированной последовательности выбора проекта и управляет версиями до статуса Approved. Prompt Builder вручную объединяет brief, pack, выбранные objects и действия в единый prompt. AI Translator концептуально адаптирует подтверждённые действия и контекст к model-specific prompt, после чего используется выбранная внешняя AI-модель. Результат проходит review, revision versions и получает статус Approved.

Все перечисленные Engine — логические роли и workflow-описания, а не реализованные программные модули. Архитектурно разделяются Creative Context, Decision Model, Engine и Structured Result. Для Engine действуют единая ответственность и независимость; Engine не изменяет результаты предыдущих Engine и не принимает окончательное решение самостоятельно. Разделяются профессиональные роли, зоны ответственности и интеллектуальные контракты. Для structured result необходим единый контракт.

## Methodology

### Базовые принципы работы

- **Knowledge First, Code Second:** сначала создаются и проверяются знания, их структура и сценарии применения; техническая реализация следует после этого.
- **Practical Workflow Second, Code Third:** после знаний приоритет имеет проверяемый пользовательский workflow, а не ранняя разработка кода.
- **Context before Creation:** решения начинаются с цели, контекста и критериев успеха.
- **Communication before Design:** сначала определяется коммуникация, затем её выразительные средства и дизайн.
- **Clarity over Complexity / Simplicity over complexity:** ясность и простота важнее неоправданной или преждевременной сложности.
- **Human-centered interaction / Human-centered Communication:** система не требует умения писать промпты; коммуникация проектируется для конкретной аудитории и её восприятия.
- Творчество служит коммуникационной цели, а не является самоцелью; смысл предшествует выразительным средствам.
- Рекомендация ориентируется на наиболее эффективный путь к заявленной цели, а не только на формально запрошенное средство. Релевантные наблюдения сообщаются, не отменяя исходную задачу.
- Профессиональная ответственность требует учитывать риски снижения эффективности; окончательное решение остаётся за клиентом или заранее определёнными правилами автоматизации.
- Профессиональные выводы должны быть структурированы и передаваемы между ролями.
- Повторное использование знаний и компонентов применяется, когда оно уместно.
- Будущие решения должны быть понятны, прозрачны и легко поддерживаемы.

### Проектирование коммуникации

Создание начинается с понимания контекста, задач клиента и потребностей аудитории. Коммуникация учитывает исходное и желаемое эмоциональное состояние аудитории, её потребности, психологические барьеры и факторы доверия. Информационная иерархия, readability и cognitive load определяют понятность и лёгкость восприятия.

Творческая концепция фиксирует коммуникационную и визуальную стратегии, порядок восприятия ключевой информации, цель, сообщение, ограничения и ожидаемый эффект. Каждое ключевое творческое решение обосновывается его влиянием на понимание, восприятие и действие человека, а не только эстетикой.

Creative Rationale связывает бизнес-задачу, потребность аудитории, основное сообщение и выбранное коммуникационное направление; показывает, как решение снижает барьеры, формирует доверие и ведёт к желаемому действию. Call To Action определяет ожидаемое действие после восприятия сообщения. Коммуникация должна дать понятное восприятие основного сообщения и поддержать переход аудитории от исходного состояния к желаемому.

Прозрачность позволяет оценивать решение по критериям успеха, а не только по эстетике. Creative Specification фиксирует целостную концепцию, необходимую для подготовки конечного продукта.

### Управление развитием и изменениями

- Развитие происходит постепенно, по реальной потребности; каждый этап имеет одну законченную проверяемую задачу.
- Не создаются функции, каталоги, сервисы, интеграции или подсистемы «на будущее».
- Любое архитектурное изменение сначала предлагается и обсуждается, затем реализуется только после утверждения.
- Новый модуль, категория, тип pack, объектный тип, каталог или интеграция не добавляется без текущей утверждённой необходимости.
- Новые знания возникают из реальной работы: необходимость фиксируется, обсуждается и лишь затем оформляется отдельным объектом.
- Новые подходы сначала проверяются на FOHOW.
- Поля и названия секций стандарта объекта не изменяются произвольно. В relations допускаются только утверждённые типы и ссылки на реальные объекты; для отсутствующей цели используется `(TODO)`.
- Pack следует `PACK_STANDARD.md`; новые pack-ы и изменения состава вводятся постепенно после утверждения.
- Пользовательский запрос сначала уточняется и нормализуется, затем сопоставляется с объектами и действиями и только после этого включается в prompt. Prompt является результатом структурированной сборки, а не навыком, обязательным для пользователя.

## Studio

VisualMind Studio — профессиональная среда разработки рекламной коммуникации. Она преобразует контекст проекта и результаты исследования в понятную, обоснованную и производимую коммуникационную концепцию.

Studio объединяет исследование, профессиональный анализ и формирование коммуникационной концепции. Её ценность — обоснованные рекомендации, ориентированные на цель клиента, аудиторию и измеримый результат. Творческая работа остаётся ответственным профессиональным процессом, а окончательное решение сохраняется за клиентом.

К Studio относятся:

- методология анализа рекламной задачи и профессиональная разработка рекламной коммуникации;
- модель восприятия аудитории, эмоциональные состояния, барьеры и факторы доверия;
- коммуникационная и визуальная стратегии;
- Creative Specification;
- оценка ясности, readability, cognitive load и ожидаемой реакции аудитории;
- Design Intelligence Report.

Design Intelligence Report — структурированное объяснение профессиональной логики коммуникационного решения. Он связывает цель, аудиторию, сообщение, эмоциональное направление, барьеры, факторы доверия, визуальную стратегию и ожидаемую реакцию аудитории; служит основанием для прозрачной оценки творческого решения.

## Повторения и пересечения, объединённые в MASTER ARCHITECTURE

- Оба документа требуют human-centered подхода: в AI VisualMind — взаимодействия без навыка prompt writing, в Studio — проектирования коммуникации для восприятия конкретной аудитории.
- Оба документа закрепляют приоритет ясности над сложностью; единая формулировка помещена в Methodology.
- В обоих документах решения опираются на структурированный контекст: AI VisualMind структурирует знания и brief, Studio — цель, аудиторию, исследование и критерии успеха.
- Structured brief / result, Creative Brief, Creative Specification и Design Intelligence Report пересекаются как средства прозрачного, передаваемого обоснования. Их архитектурные роли, методологическая логика и Studio-артефакты разделены по соответствующим разделам.
- Логические Engine AI VisualMind и Studio Decision Model пересекаются требованиями к независимости ролей, структурированному результату и отсутствию самостоятельного окончательного решения Engine.
- Reference-first validation на FOHOW и Studio-ориентация на измеримый результат совместно задают проверку решений на практике, но FOHOW остаётся архитектурным Reference Project.

## Противоречия

Прямых противоречий между документами не обнаружено.

Требующее учёта различие статусов: Studio формулирует требования, которые «должны перейти в архитектуру» (разделение Creative Context, Decision Model, Engine и Structured Result, контракт результата и ограничения Engine), тогда как Architecture Summary фиксирует, что Engine пока являются только логическими ролями и workflow-описаниями, а программная реализация не начата. Это не противоречие: первое задаёт архитектурное требование, второе — текущую границу реализации.
